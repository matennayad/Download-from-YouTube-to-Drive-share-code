# הורדת ערוצים שלמים

תוספת לשירות הקיים. ההורדה של סרטון בודד (`/download`) לא השתנתה.

## למה עבודה ברקע ולא בקשה רגילה

הורדת ערוץ לוקחת דקות עד שעות. Apps Script מוגבל ל-6 דקות להרצה,
ולדפדפן אין סבלנות לבקשה כזו. לכן:

1. הלקוח פותח **עבודה** ומקבל מיד `jobId`.
2. השרת מוריד **סרטון אחד בכל רגע**: הורדה → העלאה לדרייב →
   מחיקה מיידית מהדיסק המקומי. כך אף פעם לא נשמר יותר מקובץ אחד.
3. הלקוח בודק התקדמות דרך `GET /job/<id>`.

## איפה הקבצים נשמרים

תיקייה בדרייב על שם הערוץ (או שם הפלייליסט), בתוך
`DRIVE_FOLDER_ID`. הרצה חוזרת של אותו ערוץ נכנסת לאותה תיקייה.

בתוך התיקייה נוצר `log.txt` שמתעדכן אחרי כל סרטון, ובו שורה
לכל סרטון: מזהה, **שם הסרטון** (גם למי שלא ירד), ומה קרה —
✅ ירד / ❌ נכשל + סיבה / ⛔ חסום / ⏳ טרם נבדק בנטפרי /
⚠️ הבדיקה לא הושלמה. לכל סרטון שלא ירד מצורף קישור אליו ביוטיוב,
ולמי שירד — הקישור לדרייב. בסוף הקובץ רשימת המזהים שירדו, להעתקה.

התיקייה משותפת אוטומטית (הרשאת קריאה) למייל המבקש.

## מניעת הורדות כפולות

השרת לא מנהל היסטוריה. הלקוח שולח `skip_ids` — רשימת המזהים
שכבר ירדו אצלו — והשרת מדלג עליהם ובוחר את הבאים בתור.
כל תשובת סטטוס מחזירה `downloadedIds` שהלקוח מוסיף לרשימה שלו.

**רק הצלחות נזכרות.** סרטון שנכשל, נחסם או שהבדיקה שלו לא הושלמה
לא נכנס לרשימה, ולכן יוצע שוב בבקשה הבאה — חשוב במיוחד ל-`PENDING`,
שעשוי להפוך ל-`OPEN` אחרי שייבדק.

**חלון הסריקה גדל מעצמו.** ברירת המחדל היא 300 הסרטונים האחרונים,
אבל ככל שהלקוח שולח יותר `skip_ids` החלון מתרחב
(`len(skip_ids) + 3×התקרה`, עד `MAX_CHANNEL_SCAN_LIMIT`). בלי זה
מי שהוריד 300 סרטונים היה מקבל "אין חדשים" לנצח.

## בדיקת חסימה (נטפרי)

השירות (אופציונלי, מוגדר ב-`BLOCK_CHECK_BASE_URL`): `GET <כתובת השירות>/<מזהה>` — מזהה בלבד,
לא כתובת מלאה. מחזיר מילה אחת:

| תשובה | משמעות | מה עושים |
|---|---|---|
| `OPEN` | פתוח | מורידים |
| `LOCK` | נבדק ונחסם | לא מורידים, נרשם בלוג |
| `PENDING` | טרם נבדק (חסום בפועל) | לא מורידים, נרשם בלוג בנפרד |
| `ERROR:…` + קוד ≠ 200 | הבדיקה לא הושלמה | לא מורידים, נרשם כ"בדיקה לא הושלמה" |

שגיאה איננה תוצאה — היא לא אומרת חסום ולא פתוח, ולכן לא מורידים.
על `rate_limited` (429) יש ניסיון חוזר אחד אחרי `BLOCK_CHECK_RETRY_DELAY`
שניות. המגבלה היא 30 בקשות ל-10 שניות, וההשהייה של 4 שניות בין
סרטונים מרחיקה אותנו ממנה גם כשכל סרטון נבדק.

**הסדר בהורדת ערוץ:**

1. הערוץ מורחב תחילה — כך מתקבל מזהה הערוץ האמיתי (`UC…`) מ-yt-dlp,
   שעובד גם עבור כתובות `/c/name` ו-`/user/name` ישנות.
2. הערוץ נבדק פעם אחת.
3. `OPEN` → אף סרטון לא נבדק בנפרד.
   כל תשובה אחרת → **כל סרטון נבדק לחוד**.

**פלייליסט לא נבדק ברמת האוסף** — הסרטונים בו יכולים להגיע מכמה
ערוצים, ולכן כל סרטון נבדק לחוד.

## נקודות קצה חדשות

כולן דורשות `X-API-KEY`.

### `POST /channel/preview`
מה *היה* יורד, בלי להוריד. משמש להצגת "נמצאו N סרטונים חדשים".

```json
{ "url": "https://www.youtube.com/@example",
  "skip_ids": ["abc123"], "max_videos": 20 }
```

### `POST /channel/download`
פותח עבודה ומחזיר מיד.

```json
{ "url": "https://www.youtube.com/@example",
  "email": "user@example.com",
  "format": "audio",
  "skip_ids": ["abc123"],
  "max_videos": 20,
  "netfree": true }
```

תשובה: `{ success, jobId, channel, total, scanned,
alreadyDownloaded, remainingAfter, channelOpen, videos[] }`

אם אין סרטונים חדשים: `{ success: true, nothingNew: true }`.

### `GET /job/<id>`
`?items=0` כדי לא להחזיר את רשימת הסרטונים המלאה.

```json
{ "status": "running", "total": 20, "done": 7, "failed": 1,
  "blocked": 0, "processed": 8, "percent": 40,
  "folderLink": "...", "downloadedIds": [...] }
```

`status`: `queued | running | done | error | cancelled`

### `POST /job/<id>/cancel`
הסרטון הנוכחי מסתיים ואז העבודה נעצרת.

## משתני סביבה

| משתנה | ברירת מחדל | מה זה |
|---|---|---|
| `MAX_VIDEOS_PER_JOB` | 30 | תקרת סרטונים לבקשה |
| `CHANNEL_SCAN_LIMIT` | 300 | חלון סריקה מינימלי |
| `MAX_CHANNEL_SCAN_LIMIT` | 10000 | תקרה עליונה לחלון הסריקה |
| `DELAY_BETWEEN_VIDEOS` | 4 | שניות בין סרטונים (נגד חסימת IP) |
| `MAX_CONCURRENT_JOBS` | 1 | עבודות במקביל |
| `MAX_CONSECUTIVE_FAILURES` | 5 | עצירה אחרי כשלונות רצופים |
| `JOBS_DIR` | temp | איפה נשמר מצב העבודות |
| `BLOCK_CHECK_BASE_URL` | ריק (כבוי) | שירות בדיקת החסימה |
| `BLOCK_CHECK_TIMEOUT` | 20 | שניות |
| `BLOCK_CHECK_RETRY_DELAY` | 4 | המתנה לפני ניסיון חוזר על 429 |

## לפני העלייה לאוויר

1. אין תלויות חדשות — `requirements.txt` ו-`Dockerfile` לא השתנו.
2. אין משתני סביבה חדשים **שחייבים** להגדיר; כל החדשים הם עם
   ברירת מחדל סבירה.
3. אחרי הפריסה: `GET /` אמור להחזיר `channel_downloads.enabled: true`.
4. בדיקה ראשונה מומלצת — `POST /channel/preview` על ערוץ קטן.
   אם הוא מחזיר את שם הערוץ ומספר סרטונים, כל השרשרת עובדת.

## מגבלות שחשוב להכיר

- **העבודות חיות בזיכרון התהליך.** redeploy או קריסה מאבדים עבודות
  שרצות. בעליית השרת `cleanup_stale_jobs` מסמנת אותן ככשלון עם
  הסבר, כדי שהלקוח יקבל תשובה ברורה במקום להמתין לנצח. הקבצים
  שכבר עלו לדרייב נשארים, והמזהים כבר נשמרו אצל הלקוח, ולכן בקשה
  חוזרת ממשיכה מהנקודה שבה נעצרה. קבצי עבודות נמחקים אחרי 7 ימים.
- **התצוגה המקדימה לא בודקת חסימה.** המספר שמוצג למשתמש הוא כמה
  סרטונים חדשים יש, לא כמה מהם עברו בדיקת נטפרי. הבדיקה מתבצעת
  בזמן ההורדה עצמה.
- **חייב לרוץ בתהליך אחד.** אם מוסיפים gunicorn עם כמה workers,
  כל worker יקבל תור משלו והסטטוס יישבר. להשאיר `python3 app.py`,
  או לעבור ל-Redis/DB.
- **תקרה של 30 היא הגנה, לא הגבלה טכנית.** אפשר לשלוח את אותו
  ערוץ שוב ושוב; המערכת מדלגת על מה שכבר ירד.
- **הורדה מאתרי טלוויזיה ישראליים (מאקו, כאן 11, 13tv, n12).**
  הכותרות והעוגיות נלקחות מפרופיל לפי האתר האמיתי של הבקשה —
  לא עוד Referer של מאקו על כל האתרים. אם סריקת הדפדפן לא
  מוצאת קישור, הבקשה נופלת ל-yt-dlp ישירות במקום להיכשל מיד,
  ונתפסות גם זרימות mp4 רציפות (כאן 11). אודיו מ-HLS נשמר
  ל-m4a תקין במקום mp3 פגום.
- **אימות זרמים בתוך הדפדפן.** במאקו VOD יש גם פלייליסטים של
  פרסומות שמחזירים 403 מחוץ לנגן — והם נראים בדיוק כמו הזרם
  האמיתי. כל מועמד — כולל כאלה שנתפסים בתוך גוף תשובת API —
  נבדק עכשיו בתוך קונטקסט הדפדפן (עם העוגיות
  והכותרות שלו) לפני שנשלח להורדה: רק פלייליסט שחוזר 200 עם
  `#EXTM3U` עובר. מועמדים משרתי תוכן (keshet-vod וכד') מדורגים
  גבוה, ופרסומות מסוננות לפי שם. אם כל המועמדים נפסלים —
  נשלח ללקוח שגיאה ברורה במקום 403 מסתורי.
- **פתרון סדרה → פרק דרך ארכיון ה-web.** עמודי השער של סדרות
  מאקו מוגנים באתגר hCaptcha של Radware שדפדפן אמיתי לא עובר,
  בעוד עמודי VOD עצמם עוברים את האתגר האוטומטי. כשמתקבלת כתובת
  סדרה + season + episode, השירות לא נוגע ב  עמוד השער בכלל:
  הוא שולף מ-web.archive.org צילום של עמוד השער, ממפה
  "פרק N" לקישור ה-VOD הישיר של הפרק, וממשיך בזרימת ה-VOD
  הרגילה. אין צילום או שהפרק חדש מדי? מוחזרת שגיאה ברורה
  עם הכיוון לשלוח את קישור ה-VOD הישיר. הסריקה עצמה מנסה
  עד שלוש פעמים עם הפסקות - Radware מתנהג בצורה לא עקבית
  בין בקשות. ארכיון ה-web יורד מדי פעם לגמרי או שאין לו
  צילום עדכני - ואז נשלף עמוד השער **החי** דרך r.jina.ai
  (קורא אתרים שעובר את הגנת Radware מכתובות ה-IP שלו),
  באותו מבנה עוגנים ובאותו מיפוי "פרק N".
- **נתיב API ישיר למאקו VOD.** הנגן של מאקו מקבל את רשימת
  המדיה מ-`playlist12.jsp` בתשובה מוצפנת AES, ומפענח אותה בצד
  הלקוח. הסריקה עושה בדיוק את אותו דבר: שולפת את התשובה מתוך
  קונטקסט הדף (כולל עוגיות Radware שעברו את ההגנה) ומפענחת
  אותה עם WebCrypto בתוך הדפדפן. זה דטרמיניסטי — לא תלוי
  בלחיצות על הנגן או בהתחלת ניגון. האימות של הפלייליסטים במאקו
  רץ גם הוא בתוך הדף (fetch של הדפדפן — טביעת TLS אמיתית).
  שירות הטיקטים (mass.mako.co.il) מנפיק hdnea גם לתבניות
  cloudfront, לא רק akamaized — שימו לב ש-CDN מסוים עשוי
  לדרוש שם פרמטר שונה (cloudfront מצפה ל-`token=` ולא `hdnea=`
  וטיקט אקמאי לא תקף שם), ולכן מועמדי akamaized מדורגים קודם.
- **רשימת פרקי עונה - `POST /episodes`.** לסדרת מאקו + מספר עונה
  מחזיר את כל הפרקים: `[{"episode": 1, "url": "...VOD-....htm"}, ...]`
  - אותם מקורות של פתרון פרק בודד (ארכיון ה-web, ואז r.jina.ai),
  ואותו מטמון - בקשת הורדה אחרי רשימה לא גוררת גישה כפולה
  לארכיון. עוזר להוריד עונה שלמה בלולאה: שולפים את הרשימה,
  ואז שולחים כל קישור VOD ל-`/download` כרגיל.
- **עונה שלמה בבקשה אחת - `all_episodes` ב-`/download`.**
  (גם מהטופס: קישור סדרת מאקו בשדה הקישור מזוהה אוטומטית
  ונפתח כעבודת עונה; "כתובת 2" בוחרת עונה, ובלי מספר - עונה 1.
  המעקב, הסיום והמייל זהים לעבודות ערוץ.) כל פרק נפתר קודם
  לפלייליסט מאומת (hdnea) לפני ההורדה - בלי זה yt-dlp מקבל
  403 מ-Radware. שמות הקבצים ייחודיים: "שם-הסדרה - פרק N.ext",
  וזרמי m3u8 מקבלים שם מתוך כתובת הפלייליסט
  (למשל "Nutuk Clean - עונה 1 פרק 1") במקום "m3u8_stream".

  ```json
  { "url": "https://www.mako.co.il/mako-vod-keshet/nutuk_drama",
    "season": 1, "all_episodes": true, "format": "video",
    "email": "user@example.com" }
  ```

  פותח עבודת רקע (אותו תשתית של עבודות ערוץ) שמורידה פרק אחד
  בכל רגע: פתרון פרק → וידאו → העלאה לתיקיית דרייב בשם
  "שם-הסדרה - עונה N" → מחיקה מהדיסק. מתקדמים דרך `GET /job/<id>`
  (מחזיר `kind: "season"`, `series`, `season`, `done`, `failed`,
  `percent` ופירוט פרק) וביטול דרך `POST /job/<id>/cancel`.
  העונה חייבת `season` מספרי; `skip_episodes` (רשימת מספרים)
  מדלג על פרקים שכבר ירדו, והתקרה היא `MAX_EPISODES_PER_JOB`
  (ברירת מחדל 50). כישלון פרק לא עוצר את העבודה; 5 כשלונות
  רצופים עוצרים אותה עם הסבר, ואפשר להמשיך עם `skip_episodes`.
- `/tampermonkey-download` היה מוגדר אחרי `app.run()` ולכן מעולם
  לא נרשם כ-route. זה תוקן — הוא זמין עכשיו.

## טופס חיפוש קישורים (טופס שני)

טופס גוגל שני, "חיפוש קישורים", מוביל לאותו צינור עיבוד במלואו:

- **קישור סדרת מאקו** → עונה שלמה כעבודת רקע (עונה לבחירה בסוף
  הקישור: רווח ומספר; בלי מספר - עונה 1).
- **קישור ערוץ/פלייליסט ביוטיוב** → עבודת רקע כרגיל.
- **קישור סרטון בודד** → הורדה מיידית (וידאו/אודיו/שניהם).

אין כפילות לוגיקה: כל שורה בגיליון "חיפוש קישורים" מוזרקת לגיליון
"תגובות לטופס 1", ושם כל הכללים הקיימים חלים כמו שהם - רשימת
המאושרים, המכסות האישיות והגלובלית, נטפרי, עונות וערוצים. הסטטוס
הסופי מוחזר לעמודת הסטטוס בגיליון החיפוש, כולל מעקב "🔄 בטיפול"
לבקשות שעדיין רצות.

### התקנה חד-פעמית

1. להריץ בעורך הסקריפט את `installSearchLinksForm()` - הוא יוצר
   את הטופס, מחבר אותו לגיליון ומדפיס את הכתובות לשיתוף.
2. אין להתקין טריגר ידנית: `checkSearchLinksFormResponses` רץ כל
   5 דקות, והטריגר שלו מתקין את עצמו מחדש אם נעלם (ראו גם
   `ensureSearchLinksCheckTrigger` בתוך `pollChannelJobs`).
3. בדיקה מהירה: להריץ `TEST_ProcessSearchLinksNow()` אחרי מילוי
   הטופס - השורה אמורה לעבור מ"ריקה" ל"🔄 בטיפול (שורה N)" ואז
   לסטטוס סופי, כמו בטופס הראשי.
